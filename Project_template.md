# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователь может включать систему отопления
- Пользователь может отключить систему отопления
- Пользователь может обновить настройки системы отопления
- Пользователь может выставить необходимую температуру

**Мониторинг температуры:**

- Пользовательское приложение может запросить текущею температуру
- Пользовательское приложение может запросить текущие настройки системы отопления

### 2. Анализ архитектуры монолитного приложения

- Язык программирования: Java
- База данных: PostgreSQL
- Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
- Взаимодействие: Синхронное, запросы обрабатываются последовательно.
- Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
- Развёртывание: Требует остановки всего приложения.
### 3. Определение доменов и границы контекстов

#### 1. HeatingSystem - основная сущность системы отопления
- Свойства: id, isOn, targetTemperature, currentTemperature
- Ограничения: температура 5-35°C, проверка статуса при изменениях (в данный момент нет никакой валидации, температуру можно задавать даже если система отопления выключена)
#### 2. Сущности (Entities)
- TemperatureSensor - датчик температуры
#### 3. Сервисы предметной области (Domain Services)
- HeatingControlService - управление логикой отопления
#### 4.События предметной области (Domain Events)
- HeatingSystemTurnedOn/Off - события изменения состояния
- TemperatureChanged - событие изменения температуры
#### 5.Репозитории (Repositories)
- HeatingSystemRepository, TemperatureSensorRepository(не нашел по коду где используется) - работа с хранилищем данных

### 4. Проблемы монолитной архитектуры в сервисе управления отоплением

### 1. Масштабируемость
- **Вертикальное масштабирование** При увеличении нагрузки требуется масштабировать весь монолит, даже если нагрузка только на один модуль (например, сервис отопления).
- **Горизонтальное масштабирование** неэффективно. Копии приложения запускаются целиком, что приводит к избыточному использованию ресурсов.
- Невозможно масштабировать отдельные функциональные модули

### 2. Связанность компонентов
- Общая база данных для всех сервисов
- Прямые вызовы между модулями без четких контрактов
- Изменения в одном модуле могут затронуть другие

### 3. Надежность
- Единая точка отказа - падение одного компонента влияет на всю систему
- Нет изоляции ошибок между функциональными блоками
- Сложности с обеспечением отказоустойчивости

### 4. Разработка и внедрение
- Долгий цикл разработки из-за необходимости полного тестирования
- Конфликты при работе нескольких команд над одним кодом
- Сложности с частичным обновлением технологий

### 5. Технические ограничения
- Накопление скрытых зависимостей между модулями
- Долгий запуск большой монолитной системы
- Трудности с точечной оптимизацией компонентов
